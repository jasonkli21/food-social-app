# Goodfork next phase

## Product outcome

A diner can go from a dish, a friend's review, or a clip to a credible dinner choice, save it, then record and compare the experience. A verified manager can correct the facts that affect that decision, find reviews that need a response, and submit a clearly attributed public reply. Both paths use one canonical restaurant record. Review authorship, the freshness of listing information, and the origins of recommendations stay visible where they affect a choice.

Keep the existing React Native and Expo app, with iOS as the first device target and Android-compatible feature paths. Keep the Go API on Cloud Run, Neon Postgres, private GCS, distinct service identities, Google sign-in, and verified independent email/password accounts. Preserve the cream, marigold, and editorial typography. Build and exercise the entire phase using sample data or a locally seeded shared API. Cloud credentials are needed for deployment checks.

## Independent baseline review

The baseline has useful boundaries already. The Expo app has a typed service contract and a sample implementation. The Go API uses parameterized queries, bearer sessions with hashed tokens, single-use email verification, Google state and PKCE, and server-side ownership checks. Migrations are transactional and serialized. Account deletion cascades through most user content, and the private media proxy checks parent visibility before opening an object. These are sound primitives for the next phase.

### Decisions for this implementation

- Connect the product loops directly. A dish in a review or a clip opens Explore with that dish selected, and a suggestion links to both its restaurant and any visible supporting review. After logging a visit, preselect it in the optional comparison. Owners can see and correct their listing where diners see it, and queue items carry both the restaurant and the submitted revision.
- Keep model outputs structurally narrow. The remote dining adapter sees categories derived locally plus an explicit per-request permission flag. Literal search terms stay on the server. The remote reply adapter chooses from a bounded set of response structures for local topics and tone. Go composes the draft from approved phrases. The operator can configure independent endpoints, model IDs, and credentials through one HTTPS JSON protocol. A deterministic result remains available in both app modes.
- Sanitize new JPEG and PNG photos by decoding and re-encoding within pixel and byte limits. Accept new H.264 clips with optional AAC audio in MP4 or MOV, check required track and movie structure, and discard common container metadata without moving media offsets. Other formats get a specific error. Keep manual moderation and the public-launch gate for device-tested renditions and broader metadata normalization. Old stored objects retain their published or private status.
- Return a revision conflict before modifying an owner listing or reply with an outdated editor. A listing conflict can reload the latest facts and keep the current form available for an explicit retry. Claim decisions and post publication require the exact queue version. Reply removal uses the reported reply version, including after a deletion and recreation.
- Use a stable chronological tuple for Following, clips, restaurant review pages, and the owner inbox. The personalized feed ranks a recent bounded set. Directory list and map share the same results and explicit filters. Keep versioned API additions compatible with guests and existing readers. Version preconditions apply to sensitive writes in the updated client.
- Treat the availability of real iOS, cloud, SMTP, and Google behavior as separate release evidence. Run local checks against the app's ordinary browser and connected API entry points. The main session will record implemented work and the remaining environment-dependent checks in this report.

## Immediate implementation

The phase fits four connected threads of work. A given screen should serve one practical task, and the user should be able to do it without configuring AI or location permissions.

### 1. Establish trustworthy identities and writes

- Preserve both existing sign-in paths. For Google, resolve already-linked subjects. For an email collision, direct the person to sign in to the existing account first. Add an explicit Google link action from Settings, tied to that authenticated person and recent password verification, carrying its own one-time state and device-bound handoff. Consume the handoff under constraints that prevent linking one provider subject to two people. Keep the login and link paths distinct. Provide resend and precise recoverable feedback for email verification. Resend rotates the code on the same pending registration and respects shared mail, registration, and cooldown budgets. Clear local auth state on sign-out and surface a failure to revoke the server session separately.
- Add Postgres-backed budgets ahead of unauthenticated expensive operations. Use action-level ceilings plus normalized identity limits and retry delays. Rate limit on the trusted client identity only when the deployment defines one. Refresh session scopes on auth transitions. Give the API an explicit permission boundary for public, diner, owner, and operator actions.
- Version claim submissions, owner listing edits, and mutable owner replies. Approvals and declines consume the claim revision in the operator queue. Use one transaction and one place-lock order for approval, revocation, and listing/reply rights. Keep operator access outside the public API. Write an audit event with actor class, action, target, version, and time, with no business contact, review body, secret, or verification evidence in logs. Make queue decisions and role revocation inspectable.
- Preserve hidden and pending status across routine imports. Preserve owner-maintained fields for listings under active management. On stale listing edit, return a conflict and reload action with the owner's draft still available. On verified manager revocation, existing owner write permissions and reply visibility end immediately. Keep an owner's existing review of their own listing out of the public aggregate, including after a later ownership change until a moderator restores it.
- Tighten production URL and schema validation and document explicit runtime, migration, cleanup, and operator grants. Keep local credentials in local-only startup. Separate expired-record cleanup from object cleanup failures. Add release configuration checks and document the public launch gates below.

### 2. Give diners a short path from search to comparison

- In Explore, keep the restaurant search, place filters, and list/map controls. Add one contextual **Help me choose** action for a plain-language request such as “ramen in the East Village with vegetarian options.” Present the interpreted cuisine, area, price tier, or dietary option as editable inputs. Price tiers are approximate and exact prices require source data. Location denial leaves manual area and all ordinary filters available. Preserve filters and scroll on return from Place.
- Add indexed, token-based search over canonical directory fields and bounded published review dish matches. Rank exact name and name prefix ahead of other text matches. Add relevance and distance sorts, with distance available when location is known. Reach the same results from list and map. Useful no-match states offer a filter adjustment or the existing suggest-a-place path. Include searchable published text as evidence only when it was used to match a dish. Hidden, pending, or blocked reviews never provide evidence to that viewer.
- Put rating plus count, neighborhood, known price, and key contact actions together on the restaurant page. Show listing freshness when a verified manager supplies it, keep legacy hours as provided, and show “Hours unavailable” when missing. Limit restaurant claims about ingredients or dietary safety to attributed facts or diner observations. Keep recent reviews and a clear route to the source review, clip, or diner. Put this viewer's existing review or pending status directly on Place, instead of deriving it from the currently loaded review page.
- Require an explicit score on new reviews and keep text, attachment, and selected restaurant through network failures. Let the diner tap their dish from the review or clip to find similar visits in Explore. After successful posting, offer an optional comparison with one prior eligible visit or a path directly to the new review. Keep compare and want-to-go private. Saving, reviewing, and ranking use the same place ID. Preserve the one-review-per-person/place model and existing comparisons. A diner can edit the existing review.
- Keep Following separate from nearby suggestions, and show helpful restaurant choices when Discover has no reviews. Keep an active clip playable only while it is visible, foregrounded, and motion settings allow autoplay. Start muted and provide a retry plus an accessible path to its review and place. Use the optional clip description or review text for context, and make it reachable at large text sizes. Keep private byte-range reads and manual moderation. Validate byte and duration limits and the supported attachment types on the server. Open the authorized object before committing the body status so storage failure has a defined retry state. Use a known JPEG and H.264/AAC MP4 fixture to prove guest, pending-author, and deleted playback paths.

### 3. Make verified ownership a practical daily workflow

- Retain **Restaurant tools** under You and **Manage restaurant** on a managed Place. Claim from a restaurant page, view the status, and see what to do after decline or revocation. ## Implementation order and compatibility

1. **Prove the baseline** with a seeded disposable PostgreSQL database, local media, deterministic accounts, fixture restaurants in at least two areas, one existing managed listing, and one pending claim. Split focused integration cases out of the current walkthrough. Keep existing response contracts working as new fields and scoped routes land.
2. **Ship one additive migration and the write safeguards.** Introduce listing, claim, and reply revisions, audit events, and search indexes. Backfill revision defaults, keep IDs stable, and verify the migration over existing 004 data. Validate the required migration at startup. Lock with the same order across moderation, listing, and reply operations. Update local CLI instructions and the staging grants. Test grants and migration checks before UI writes rely on the schema.
3. **Implement directory and owner read paths.** Reuse existing visibility and projections where they agree with the contract. Pass lightweight summaries for lists and retain rich objects on detail. Add deterministic ordering and migrate new owner, clip, and chronological reads to cursor paging without removing legacy offset support. Bind cursor to sort and filter and make the tie-breaker a unique ID. Use a bounded date window for personalized candidates, with stable chronological pages across new arrivals elsewhere. Inspect representative query plans with a seeded dataset and add only indexes that serve the implemented queries.
4. **Wire the normal app flows and parity.** Extend `types.ts`, the connected service, and the sample service together. Update Explore, Place, Compose, Saved, Clips, and Owner through their existing navigation. Scope refresh to the operation's resources and discard responses for stale filter/session generations. Keep the new screens usable at small widths, with large text and reduced motion. Make compatibility and upload errors recoverable and avoid exposing raw private attachment URLs.
5. **Connect provider operations and verify.** Run the local provider on the same intent and reply contracts. Exercise the real HTTP adapter against a local stub. Keep sensitive routing disabled until explicitly configured. Run acceptance checks below. Record remaining device and deployment checks by environment. Review existing auth assertions that expected automatic linking and replace them with the new explicit-link contract.

Keep database/DTO changes small enough that the previous client can still read public resources during rollout. Ship the migration before routing traffic to the new revision. Keep model failure outside critical auth, directory, save, publication, and moderation paths. Use an isolated service adapter for each different provider protocol.
